# 电商评论 LLM 智能打标工具 — 项目进展记录

## 一、项目背景与目标

**目标**：构建一个基于大语言模型（LLM）的电商评论自动打标系统，支持用户通过可配置的四级标签体系，对评论数据进行批量语义分析并输出结构化标签。

**核心价值**：
- 标签体系完全外置（Excel/CSV 配置），零代码调整
- 利用 LLM 语义理解能力，解决关键词匹配无法处理的语义变体、否定转折等问题
- 支持多模型提供商（OpenAI、DeepSeek、DashScope、任意兼容 OpenAI 接口的网关）

## 三、标签体系图形化配置界面（已完成）

### 3.1 技术方案演进

| 版本 | 方案 | 问题 | 结论 |
|------|------|------|------|
| V1 | Streamlit 列表视图 | 无法全局观察整棵树 | 放弃 |
| V2 | Streamlit + Graphviz | Graphviz 图片多余，交互差 | 放弃 |
| V3 | Streamlit Finder 列视图 | 无法同时展开所有分支做全局观察 | 放弃 |
| **V4** | **纯 HTML/JS/CSS 画布编辑器** | **完全满足需求** | **采用** |

### 3.2 最终成果

**文件位置**: `app_tag_config.html`（项目根目录，浏览器直接打开即可）

**访问方式**:
```bash
# 方式一：直接打开
open app_tag_config.html

# 方式二：HTTP 服务器
cd ecommerce-review-tagger
python -m http.server 8502
# 浏览器访问 http://localhost:8502/app_tag_config.html
```

**已实现功能**:

| 功能 | 说明 |
|------|------|
| **画布式全局视图** | 整棵树同时可见，一级在左，向右层层展开，SVG 贝塞尔曲线连接父子节点 |
| **节点展开/折叠** | 有子节点的节点右侧显示 `−` / `+` 按钮，点击即可展开/折叠 |
| **单击选中 + 浮动菜单** | 单击节点高亮选中，右下方弹出菜单：添加子节点/同级节点/编辑/删除 |
| **双击直接编辑** | 双击节点名称进入 inline 编辑，回车或失焦保存 |
| **四级颜色区分** | 🔴 一级 / 🟠 二级 / 🟢 三级 / 🔵 四级 |
| **四级深度限制** | 第四级节点不能添加子节点 |
| **全部展开/折叠** | 顶部工具栏一键控制整棵树的展开状态 |
| **导入/导出 CSV** | 兼容 CLI 的 CSV 格式，支持四级标签 |
| **本地自动保存** | 保存到浏览器 localStorage，刷新不丢失 |
| **键盘快捷键** | `Enter` 弹出菜单、`Tab` 添加子节点、`Delete` 删除、`Esc` 关闭菜单 |

### 3.3 关键设计决策

1. **放弃 Streamlit**：Streamlit 的自上而下线性渲染模型无法支持自由画布 + 全局树形编辑，果断转向纯前端方案
2. **SVG 连线 + HTML 节点**：SVG 负责贝塞尔曲线连接，HTML div 负责节点交互，两者分层清晰
3. **后序遍历布局算法**：先计算叶子节点 y 坐标，父节点取子节点中点，确保树形结构紧凑美观
4. **无遮罩层菜单**：早期使用全屏遮罩关闭菜单，但会阻挡画布滚动；最终改为 document 级点击监听，点击非菜单区域自动关闭

| 后端 | FastAPI | 异步友好，天然支持 SSE 实时进度推送 |
| 通信 | REST + SSE | 文件上传/配置提交用 REST，进度推送用 SSE |
| 核心 | ExcelTagger | 完全复用 CLI 核心逻辑，零重复代码 |

### 4.3 已实现功能

| 功能 | 说明 |
|------|------|
| **拖拽上传** | 评论文件 + 标签体系文件均支持点击/拖拽上传 |
| **列名自动识别** | 上传后自动读取列名，智能猜测「评论内容」列 |
| **数据预览** | 上传后即时渲染前5行表格 |
| **LLM 配置** | 提供商/模型/API Key/自定义地址/并发数/置信度等完整配置 |
| **Prompt 预览** | 输入单条评论，实时查看发给 LLM 的完整 Prompt（调试用） |
| **实时进度条** | SSE 推送，显示已处理/总数 + 百分比 |
| **错误展示** | LLM 调用失败时完整展示错误堆栈 |
| **结果预览** | 完成后渲染前10行打标结果表格 |
| **一键下载** | 宽格式/长格式 CSV 直接下载 |
| **API 连通检测** | 顶部状态圆点实时反映后端连通性 |

### 4.4 关键设计决策

1. **复用而非重写**：后端直接调用 `ExcelTagger.tag_excel()`，通过注入 `progress_callback` 实现进度推送，核心逻辑零改动
2. **SSE 而非轮询**：Server-Sent Events 单向推送进度，比前端轮询更实时、更省资源
3. **纯前端 HTML**：与标签配置编辑器保持一致的技术栈，避免引入 React/Vue 等构建工具，降低维护成本
4. **内存任务管理**：任务状态存在内存字典中，配合临时文件目录，简单场景足够，后续如需持久化可迁移到 Redis

# 浏览器自动访问 http://localhost:8000/

## 五、Phase 2：数据质量识别（已完成）

### 5.1 目标

在打标过程中自动识别两类问题评论，避免垃圾数据污染打标结果：
1. **模糊评论** — 语义含糊、信息不足，无法准确匹配标签（如"还行吧"）
2. **虚假评论** — 刷单、模板化、水军评论

### 5.2 技术方案

| 能力 | 实现方式 | 说明 |
|------|---------|------|
| 模糊识别 | LLM Prompt 指令 | 要求模型对无法打标的评论返回 `uncertain: true` |
| 虚假识别 | LLM Prompt 指令 | 要求模型输出 `authenticity_score`（0~1） |
| 状态机 | 后端解析层 | `rejected` > `uncertain` > `normal` 自动判定 |
| 过滤保护 | 特殊标记保留 | `_uncertain` 标签项不受 confidence 阈值过滤 |

### 5.3 输出扩展

宽格式 & 长格式输出均新增三列：
- `是否模糊` (0/1)
- `真实性评分` (0.0~1.0)
- `评论状态` (normal/uncertain/rejected)

### 5.4 关键设计决策

1. **向后兼容**：原有 `_extract_json_matches` 保持签名不变，内部调用新的 `_extract_full_result`
2. **状态机下沉**：`status` 在 `_parse_responses` 中根据 `authenticity_score` 和 `uncertain` 自动计算
3. **Token 控制**：System Prompt 仅新增约 150 字，少样本示例新增 2 个但默认只取前 2 个

## 六、Phase 3：数据持久化 + 增量打标 + 人工修正（已完成）

### 6.1 目标

构建完整的数据管理闭环：持久化存储 → 增量更新 → 人工审核修正。

### 6.2 数据持久化层（SQLite）

**零 ORM 依赖**，使用标准库 `sqlite3`：

| 表 | 用途 |
|---|---|
| `tasks` | 任务元数据（ID、状态、配置、时间戳） |
| `reviews` | 评论数据（内容、content_hash、状态、模糊标记、真实性评分） |
| `tag_records` | 标签记录（四级标签、置信度、原因、是否人工修正） |

### 6.3 增量打标

`IncrementalTagger` 继承 `ExcelTagger`：
- 支持读取历史结果文件（宽表/长表自动识别）
- 匹配策略：优先 `review_id` → fallback `MD5(content)` content_hash
- 两种策略：`skip_existing`（仅打标新增）/ `re_tag_all`（全部重打）
- CLI 和 Web 两端语义一致

### 6.4 人工修正工作流

**审核模式**（Web 工作台顶部切换）：
1. 输入 task_id 加载全部评论
2. 筛选栏：按状态(normal/uncertain/rejected/reviewed)、一级标签、关键词过滤
3. 评论列表：展示内容、标签 pills、真实性评分彩色条、状态徽章
4. Inline 编辑：点击编辑 → 删除/添加标签 → 级联下拉框选择 → 保存调用 API
5. 批量操作：多选 → 批量标记已审核 / 批量删除虚假评论

### 6.5 新增 API

| 端点 | 说明 |
|------|------|
| `GET /api/tasks/{id}/reviews` | 分页获取评论及标签 |
| `POST /api/tasks/{id}/reviews/{db_id}/tags` | 人工修正标签 |
| `GET /api/tag-hierarchy?file_id=` | 获取标签体系树（级联下拉数据源） |
| `POST /api/tag`（扩展） | 支持 `previous_output_path` + `strategy` |

### 6.6 关键设计决策

1. **双写任务状态**：保留内存字典维持 SSE 实时进度，同时写入 SQLite 持久化
2. **前端分页+筛选**：审核面板一次性拉取全部数据，筛选和分页在浏览器端完成，避免数据断层
3. **标签体系 fallback**：优先从原始文件读取；文件不可读时从已加载评论标签动态构建层级树

## 十二、Phase 6：多维度标签体系映射（已完成）

### 12.1 目标

解决不同商品类目、购物环节需要使用不同标签体系的问题。例如：
- **鞋子** 关注尺码、舒适度、磨脚
- **上衣** 关注版型、面料、颜色
- **文胸** 关注罩杯、钢圈、聚拢效果
- **购前** vs **购后** 评论关注点完全不同

### 12.2 核心设计

**三个核心概念**：

| 概念 | 说明 |
|------|------|
| `TagProfile`（标签方案） | 一个标签体系文件 + 名称/描述 |
| `TagMappingRule`（映射规则） | 当 `[列名] [运算符] [值]` 时，使用 `[方案]` |
| `TagMappingConfig`（映射配置） | 多个方案 + 多条规则 + 默认方案 fallback |

**规则运算符**：`==`、`!=`、`contains`、`in`、`starts_with`、`ends_with`、`regex`

**规则匹配逻辑**：
- 同一条规则的多个条件是 **AND** 关系
- 规则之间按 **priority 降序**排列，第一条匹配即生效
- 无匹配时 fallback 到 **默认方案**

### 12.3 后端实现

| 文件 | 说明 |
|------|------|
| `src/review_tagger/core/tag_mapping.py` | 映射引擎核心（Condition/Rule/Config） |
| `src/review_tagger/core/multi_tagger.py` | 多标签体系打标器，按方案分组后分别调用 LLM |
| `src/review_tagger/api/routes.py` | 新增 4 个 API 端点 |

**新增 API**：

| 端点 | 说明 |
|------|------|
| `POST /api/tag-profiles` | 上传单个标签体系文件作为标签方案 |
| `POST /api/tag-mapping-config` | 保存映射配置，返回 config_key |
| `POST /api/tag-mapping-preview` | 预览每条评论匹配到什么方案（前50条） |
| `POST /api/tag-multi` | 启动多维度映射打标任务 |

### 12.4 前端实现

Step 1 标签体系区域重构：

- **模式切换**：「单标签体系」/「多维度映射」两个按钮切换
- **标签方案管理**：支持拖拽上传多个标签体系文件，显示方案列表（名称/行数/列数）
- **映射规则配置**：可视化规则编辑器
  - 条件行：`当 [列名下拉框] [运算符下拉框] [值输入框] 且 ...`
  - 结果行：`则使用方案 [方案下拉框]`
  - 支持添加/删除规则和条件

### 12.6 关键设计决策

1. **向后兼容**：单标签体系模式完全保留原有流程，用户无感知切换
2. **分组调用 LLM**：同方案评论共享同一标签体系 Prompt，避免每条评论都重新构建不同 Prompt 的 token 浪费

4. **内存缓存映射配置**：`_mapping_configs` 字典临时存储配置，配合 config_key 传递

## 十一、复盘要点

1. **MVP 验证有效**：LLM 打标在语义理解上确实优于规则匹配，且标签体系外置方案可行
2. **兼容性优先**：不同模型对 JSON Mode 支持不一，容错解析机制（正则兜底）非常关键
3. **配置化优先**：confidence 阈值、输出格式等做成配置项而非硬编码，提升了灵活性
4. **测试先行**：在接入真实 LLM 前先完成单元测试，节省了大量调试时间
5. **第一性原理**：当 Streamlit 无法满足画布交互需求时，果断放弃现有方案，用纯前端重写，最终效果远好于在错误方向上迭代
6. **规则引擎思维**：多维度映射本质上是「规则引擎 + LLM」的混合架构，规则负责分发，LLM 负责语义理解
